# zmk-studio-push: runtime keymap updates without reflashing

**Date:** 2026-04-08
**Status:** Approved for implementation
**Board scope:** Toucan only (Glove80 deferred)

## Problem

Editing `config/toucan.keymap` currently requires a full firmware rebuild (~1 minute via Docker) and a two-step USB flash ritual. The Toucan has ZMK Studio enabled (`CONFIG_ZMK_STUDIO=y`, `CONFIG_ZMK_STUDIO_TRANSPORT_BLE=y`, `CONFIG_ZMK_STUDIO_LOCKING=n`) so keybindings can theoretically be pushed at runtime over USB CDC or BLE GATT. The official Studio UI (zmk.studio) can do this but only via an interactive web client — there's no official CLI. A community Python CLI exists (`electronicmaterialsoffice/zmk-studio-cli`) but is self-described as a debug tool, lightly maintained, and requires per-key manual invocation.

Goal: a `make push-toucan` target that takes the authoritative `config/toucan.keymap` source and pushes all its bindings to the running firmware via RPC, with a `make pull-toucan` companion for creating JSON snapshots as rollback points.

## Approach

A self-contained Python package at `scripts/zmk_studio_push/`, driven by Makefile targets, with a repo-local venv at `.venv/`. It owns every layer of the stack so it's not blocked by upstream bitrot: devicetree parser, keycode table, message framing, dual-transport (USB serial + BLE GATT), RPC orchestration, push/pull/restore flows.

The package is organized around five concerns that communicate through minimal interfaces:

- **Parser** (`parser.py`) — converts `config/toucan.keymap` into a list of `(layer_index, key_position, behavior_name, param1, param2)` tuples.
- **Keycodes** (`keycodes.py`) — frozen lookup table mapping ZMK keycode symbols (`F7`, `C_MUTE`, `LCTRL`, ...) to their 32-bit encoded values. Generated by `scripts/regen_keycodes.py` from ZMK's `dt-bindings/zmk/keys.h`.
- **Framing** (`framing.py`) — the shared SoF/Esc/EoF codec used by both transports.
- **Transports** (`transport/{base,usb,ble,discover}.py`) — async pyserial and bleak clients behind a common `StudioTransport` interface, plus auto-detection that races USB and BLE concurrently.
- **RPC / flows** (`rpc.py`, `flows.py`, `cli.py`) — request/response orchestration and the three top-level operations: push, pull, restore.

The parser output is independent of any device; the RPC layer resolves source-code behavior names (`kp`, `mt`, ...) to runtime behavior IDs by consulting the firmware's behavior metadata on each connection. This means backup JSON files are portable across firmware rebuilds.

## Components

### `parser.py`

Turns devicetree text into a list of `ParsedBinding` tuples.

**Stages:**

1. **Preprocess** — strip `//` and `/* */` comments, collect `#define NAME value` into a symbol table (both simple integer values and multi-token text like `#define _SMART_NUM &smart_num NUM 0`), skip `#include` lines.
2. **Skip non-binding blocks** — discard `&sk`/`&sl`/`&lt`/`&mt` config override blocks, `ZMK_HOLD_TAP`/`ZMK_MOD_MORPH`/`ZMK_TAP_DANCE` helper invocations, `&num_word { ... };` config, and anything else that isn't a `layer_NAME { bindings = <...>; };`.
3. **Extract layers** — find each `layer_NAME { display-name = "..."; bindings = < ... >; };`. Layer index comes from **block order** (matching ZMK's compiled layer indexing), layer human name from the `layer_NAME` suffix.
4. **Expand macros** inside bindings text — substitute `_SMART_NUM` → `&smart_num NUM 0`, then layer names `NUM` → `3`, etc.
5. **Tokenize** — walk tokens, group each `&name` with N args where N is looked up in a static `BEHAVIOR_PARAM_COUNTS` table.
6. **Resolve args** — each arg is a numeric literal, a previously-declared `#define` value, or a keycode symbol looked up via `keycodes.py`. Modifier-wrapped keycodes like `LG(N1)` are evaluated recursively: look up the inner keycode, OR in the modifier bitmask at bits `[31:24]`.

**Static behavior param counts** (expandable — every supported behavior must be listed):

| Token | Params | Arg semantics |
|---|---|---|
| `&kp` | 1 | keycode |
| `&mt` | 2 | mod (HID keycode for modifier), keycode |
| `&lt` | 2 | layer index, keycode |
| `&mo` | 1 | layer index |
| `&to` | 1 | layer index |
| `&trans` | 0 | — |
| `&none` | 0 | — |
| `&smart_num` | 2 | layer index, 0 (hold-tap) |
| `&smart_shft` | 0 | — |
| `&key_repeat` | 0 | — |
| `&num_word` | 1 | layer index |

Any unknown `&behavior` is a hard error. Any unknown keycode symbol is a hard error. Any `#define`d name referenced but not declared is a hard error. Cell count per layer is verified against an expected value derived from the keymap's physical layout (42 keys for Toucan).

**Output:**

```python
@dataclass
class ParsedBinding:
    behavior_name: str       # e.g. "kp", "mt", "smart_num"
    param1: int              # 0 if N/A
    param2: int              # 0 if N/A

@dataclass
class ParsedLayer:
    index: int
    name: str                # "Base", "Sym", ...
    bindings: list[ParsedBinding]  # in key-position order

@dataclass
class ParsedKeymap:
    layers: list[ParsedLayer]
```

### `keycodes.py` (generated)

A frozen Python dict mapping symbolic name → ZMK-encoded 32-bit integer. Example entries:

```python
KEYCODES = {
    "A":        0x00070004,
    "F7":       0x0007003E,
    "C_MUTE":   0x000C00E2,
    "LCTRL":    0x000700E0,
    "BSPC":     0x0007002A,
    # ...
}

# Modifier bit positions (shifted left 24)
MOD_LCTL = 0x01 << 24
MOD_LSFT = 0x02 << 24
MOD_LALT = 0x04 << 24
MOD_LGUI = 0x08 << 24
# ... etc

MODIFIER_FUNCTIONS = {
    "LC": MOD_LCTL,
    "LS": MOD_LSFT,
    "LA": MOD_LALT,
    "LG": MOD_LGUI,
    "RC": MOD_RCTL,
    "RS": MOD_RSFT,
    "RA": MOD_RALT,
    "RG": MOD_RGUI,
}
```

Generator (`scripts/regen_keycodes.py`):

1. Fetches `dt-bindings/zmk/hid_usage_pages.h`, `hid_usage.h`, `modifiers.h`, `keys.h` from ZMK `main` branch (version pinned in a comment at the top of the generated file).
2. Parses `#define NAME (VALUE)` lines.
3. Evaluates expressions involving `ZMK_HID_USAGE`, `LS`/`LC`/`LA`/`LG`/`RS`/`RC`/`RA`/`RG`, `APPLY_MODS`, and integer arithmetic using a restricted Python `eval()` namespace.
4. Writes `scripts/zmk_studio_push/keycodes.py` with a header comment noting the ZMK source commit hash and generation date.

### `framing.py`

Exactly the codec from ZMK's RPC protocol docs, cross-referenced against both the upstream C implementation and the community CLI's Python version.

```python
SOF = 0xAB
ESC = 0xAC
EOF = 0xAD

def encode_frame(payload: bytes) -> bytes:
    """Wrap payload with SoF/EoF and escape any special bytes in payload."""

def decode_frame(data: bytes) -> bytes:
    """Parse a complete frame (starts with SoF, ends with EoF) and return payload."""

class FrameReader:
    """Stateful accumulator for streaming bytes.
    Used by BLE (indications arrive in chunks) and USB (byte-at-a-time reads).
    Call feed(chunk) to push data; returns complete payloads as they're parsed."""
    def feed(self, chunk: bytes) -> list[bytes]: ...
```

### `transport/base.py`

```python
class StudioTransport(ABC):
    @abstractmethod
    async def send_request(self, request: studio_pb2.Request) -> studio_pb2.Response: ...
    @abstractmethod
    async def close(self) -> None: ...
    @property
    @abstractmethod
    def name(self) -> str: ...  # "usb:/dev/tty.usbmodem..." or "ble:XX:XX:XX"
```

### `transport/usb.py`

`StudioSerial` wraps `pyserial.Serial(port, timeout=...)` (no baud rate — Zephyr CDC ACM ignores it). Reads are wrapped in `asyncio.to_thread` for the async interface. Uses the stateless `encode_frame` / `FrameReader` from `framing.py`.

Request flow:
1. `request.request_id = next_id()`
2. Serialize request to bytes
3. Encode as frame
4. Write to serial
5. Loop: read chunks from serial (via `to_thread`), feed to `FrameReader`, check for complete frames
6. For each complete frame, decode into a `Response`. If it's a `request_response` matching our `request_id`, return it. If it's a `notification`, drop and continue.

### `transport/ble.py`

`StudioBLE` uses `bleak.BleakClient`. Request flow:

1. Connect to the device at construction time
2. Subscribe to GATT indications on the Studio characteristic (UUID `00000001-0196-6107-c967-c5cfb1c2482a`); indication handler pushes chunks into an `asyncio.Queue`
3. `send_request`: serialize, encode frame, `write_gatt_char` to the Studio characteristic
4. Consume chunks from the queue via a shared `FrameReader`, return matching response

GATT service UUID: `00000000-0196-6107-c967-c5cfb1c2482a`.

### `transport/discover.py`

```python
async def discover(preference: str = "auto") -> StudioTransport: ...
```

- **`preference='usb'`:** iterate `/dev/tty.usbmodem*` (macOS) / `/dev/ttyACM*` (Linux), probe each with `core.get_device_info`, return first responder within 500ms, raise clear error if none respond.
- **`preference='ble'`:** bleak scan for ~3s, filter advertisements by Studio service UUID, probe each, return first responder.
- **`preference='auto'`:** run both concurrently via `asyncio.gather` + `asyncio.wait(FIRST_COMPLETED)`, cancel the loser, return the winner.
- **Env overrides:** `ZMK_STUDIO_PORT` or `ZMK_STUDIO_BLE_ADDR` skip discovery entirely.

### `rpc.py`

Request/response orchestration and behavior resolution.

```python
class StudioRPC:
    def __init__(self, transport: StudioTransport):
        self.transport = transport
        self._next_request_id = 1
        self._behaviors_by_display_name: dict[str, int] | None = None

    async def get_device_info(self) -> GetDeviceInfoResponse: ...
    async def list_behaviors(self) -> dict[str, int]:
        """Return display_name → id map. Cached after first call."""
    async def get_keymap(self) -> Keymap: ...
    async def set_layer_binding(self, layer_id: int, position: int,
                                behavior_id: int, p1: int, p2: int) -> None: ...
    async def save_changes(self) -> None: ...
    async def discard_changes(self) -> None: ...
```

**Behavior name resolution:** To map source-code tokens like `kp` to runtime behavior IDs, we need a map from the source token to the runtime's `display_name`. For built-in ZMK behaviors, `display_name` is explicitly set in their `.dtsi` definitions (e.g., `kp` → "Key Press", `mt` → "Mod-Tap"). For custom behaviors declared via urob's `ZMK_HOLD_TAP` helper, `display_name` defaults to the device node name (e.g., `smart_num` → "smart_num").

We hardcode the built-in map and fall through to "assume display_name equals source token" for custom behaviors:

```python
BUILTIN_DISPLAY_NAMES = {
    "kp": "Key Press",
    "mt": "Mod-Tap",
    "lt": "Layer-Tap",
    "mo": "Momentary Layer",
    "to": "To Layer",
    "trans": "Transparent",
    "none": "None",
    "key_repeat": "Key Repeat",
    "caps_word": "Caps Word",
    "sk": "Sticky Key",
    "sl": "Sticky Layer",
    "tog": "Toggle Layer",
    "bt": "Bluetooth",
    "out": "Output Selection",
    "rgb_ug": "RGB Underglow",
    "reset": "Reset",
    "bootloader": "Bootloader",
}

def resolve_behavior_display_name(token: str) -> str:
    return BUILTIN_DISPLAY_NAMES.get(token, token)
```

At push time, we fetch the runtime behavior list, build `display_name → id`, and for each parsed binding look up `resolve_behavior_display_name(token)` to get the display name and then the ID. If a display name isn't found at runtime, we abort with a clear error listing the missing behavior and the available ones.

## Backup JSON schema

```json
{
  "schema_version": 1,
  "timestamp": "2026-04-08T15:30:00Z",
  "keyboard": "toucan",
  "device": {
    "name": "toucan",
    "serial_number": "hex-encoded bytes if available"
  },
  "behaviors": [
    {"id": 0, "display_name": "Key Press", "num_params": 1},
    {"id": 1, "display_name": "Mod-Tap", "num_params": 2}
  ],
  "layers": [
    {
      "index": 0,
      "name": "Base",
      "bindings": [
        {
          "position": 0,
          "behavior_display_name": "Momentary Layer",
          "params": [4, 0]
        }
      ]
    }
  ]
}
```

**Key design decision:** bindings reference behaviors by `display_name`, not by runtime `id`. This makes backups portable across firmware rebuilds — at restore time we re-resolve the display name against the current firmware's behavior list.

## Error handling

- **Parser errors** — include file:line context, the offending token, and a hint for how to fix. All parser errors abort before any network activity.
- **Unknown behavior at parse time** — list the behavior and point at `BEHAVIOR_PARAM_COUNTS` in `parser.py`.
- **Unknown keycode at parse time** — list the symbol and suggest running `scripts/regen_keycodes.py` to refresh the table.
- **Transport discovery failure** — distinguish "no devices found" vs "devices found but none speak ZMK Studio" vs "multiple devices ambiguous". Suggest specific env var overrides.
- **Behavior resolution failure at push** — list the missing source-code behavior name, the display name we looked up, and the available display names from the runtime.
- **Structure mismatch at push** — source has different layer count or binding count per layer than the running firmware. Abort with message suggesting "rebuild + flash once, then use push".
- **RPC errors during push** — abort immediately, send `discard_changes` to clean up in-memory pending state, print which binding failed.
- **`save_changes` error** — abort, print error code, advise flashing stock firmware if the device is now in an inconsistent state.

## Testing strategy

**Unit-testable without hardware:**
- `framing.py` — random payload round-trips, edge cases (empty, single byte, all special bytes, chunk boundaries crossing escape sequences).
- `parser.py` — parse the actual `config/toucan.keymap` and spot-check specific bindings. Parse crafted minimal fixtures for each binding type.
- `keycodes.py` — spot check 10–15 symbols against manually-verified values.
- `rpc.py` behavior-name resolution — test with a fake behavior map.
- JSON backup serialization — round-trip test.

**Requires hardware (deferred to user testing):**
- USB transport end-to-end
- BLE transport end-to-end
- Auto-discovery
- Push/pull/restore against a real device

**Coverage target:** ~70% of the code (all parser logic, all framing logic, all serialization logic). The transport layer is thin enough that mocking pyserial/bleak doesn't add much value beyond type checks.

Tests live in `scripts/zmk_studio_push/tests/` and run with `pytest`.

## Out of scope

- Glove80 support (same implementation would apply; just add targets and route a different keymap path)
- `add_layer` / `remove_layer` / layer reordering — push is structure-preserving only
- Editing hold-tap timings, mod-morph configurations, macros — Studio RPC doesn't expose these
- Interactive mode / REPL
- Watch mode (auto-push on file change)

## Known caveats to communicate to the user

1. **Studio vs. source sync:** Once `push` is used, the device's settings partition holds the in-memory representation. Subsequent firmware flashes wipe those in-memory changes (stock firmware is reloaded). Users should treat `config/toucan.keymap` as the source of truth and `push` as a fast iteration mechanism, not as a substitute for rebuilding and flashing when changes should be permanent.
2. **BLE vs. USB:** Auto-detect races both. USB typically wins when plugged in. BLE wins when wireless.
3. **Structure mutations still require a rebuild:** Adding a new layer, adding a new custom behavior, or changing the physical layout all require rebuilding firmware. Push is for reassigning existing bindings to different behaviors.
4. **Behavior name maintenance:** When adding a new custom behavior to the source, add its `&name` → param count entry to `BEHAVIOR_PARAM_COUNTS` in `parser.py`. The cross-check at push time will fail loudly otherwise.
